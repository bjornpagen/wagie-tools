# Schema baselines and cutovers

`migrations/0002-typed/` is the current baseline. `migrations/index.ts` lists
every released step as data: its source schema, target schema and cutover
function. `migrations/current.ts` names the baseline the runtime opens.
`0000-initial/` is the first baseline:

- `schema.json` is the native-verified schema snapshot.
- `schema.ts` is generated by Log from that snapshot. Do not edit or format it by hand.
- `cutover.ts` is an ordinary typed function copying all ordinary relations into
  native unpublished population. Closed facts come from the verified schema.

The initial cutover preserves every fact and entity ID. It creates no company,
policy, payment, or filing records. Fresh empty histories use `LocalHistory.create`
with the same canonical snapshot and obtain their business facts separately.

## 0001-statements

The second baseline changes representation, not facts:

- `Statement { id, text }` holds every distinct piece of prose once. Its id is a
  UUIDv8 carrying the text's SHA-256 (`statementId` in `src/commands.ts`), so the
  same words written by any command are the same fact. Every former
  `evidence: str` column is now `evidence: uuid` into Statement.
- `recordedAt`/`verifiedAt` columns are gone; UUIDv7 ids are the clock. Rows that
  had a timestamp but no id gained an id.
- `Question` is one header (`kind`, `detail`) with exactly one typed arm per kind
  (`EmployeeQuestion`, `PlanQuestion`, `BookkeepingQuestion`, `AccountQuestion`)
  under `alternatives`, and `Answer` closes it. It replaces Review/Resolution,
  RetirementSetup/…Resolution, BookkeepingIssue/…Resolution and
  FinancialIssue/PaymentIssue/FinancialResolution.
- `DriveCopy` is the verified permanent copy of an artifact; `PriorLocation`
  keeps the locations it superseded. The JSON that used to live inside a
  location's evidence string is gone.
- `TaxBand.span` is `TaxBand.wages`; `BankObservation.source` is `evidence`;
  `NegativeApplication` holds the evidence for applying a negative liability.

`migrations/0001-statements/cutover.ts` is the transformation. It preserves
every entity id and carries its own frozen copy of the 0001 filing digest.

## 0002-typed

The third baseline gives every column a type that says what it is:

- Closed rosters replace strings that always held one of a fixed set:
  `Employee.filingStatus` (FilingStatus), `BusinessAddress.kind` (AddressKind),
  `SuppliedConversionTax.field` (ConversionTaxField), `SignedDisposition.disposition`
  (Disposition), `PaymentReference.issuer` (PaymentIssuer).
- `BankReference` is gone; every row restated `MercuryTransaction`.
- `PaymentReference.scope` (a uuid in a string) is `account: uuid`, contained in
  its payment; `sourceText` is gone (it was the value or a passage of the payment's evidence).
- `AttestedVersion.attestation` and `GrandfatheredEligibility.attestation` are
  `evidence` Statements.
- `RetirementReport.supplied` (a JSON blob) is a `form` header with typed arms
  under `alternatives`: `Reported1099R` (+ `Reported1099RBasis` for box 5) and
  `Reported1096`.
- `cents` columns are named by role: `PolicyLimit.amount`,
  `ElectionDocumentAmount.amount`, `CalculationBasis.gross`,
  `CalculationWageBase.gross`.

`migrations/0002-typed/cutover.ts` refuses if any live row carries information
its new shape cannot hold (a reference whose scope is not the payment's account,
a report whose stated account kind disagrees with the account). Retirement
filing digests are re-derived with the current function.
`test/migration.test.ts` seeds a synthetic 0000 history and runs both steps.

## Schema tooling

Each baseline's artifacts are generated with the published tools:

```sh
pnpm schema:generate   # snapshot + bindings for the current baseline
pnpm schema:check
```

`pnpm schema:generate` invokes those two generators. Generation performs no
database I/O. Preserve released snapshots. For the next schema: add a migration
directory, point `schema:generate` at it, write the cutover against the two
generated schemas, add the step to `migrations/index.ts`, and set
`migrations/current.ts`. The current step's target is the live `ledger` object
itself; `pnpm schema:check` proves the generated artifact beside it is the same
schema. There is no plan DSL, module discovery, or automatic migration on
startup.

```sh
node scripts/migrate.ts --step 0002-typed --binding private/binding.json \
  --contract private/migration/contract-0002.json --out private/migration
node scripts/migrate.ts --step 0002-typed … --activate
```

## Operator scripts

- `scripts/migrate.ts --step NAME` runs one released cutover (below).
- `scripts/facts.ts --binding FILE --out FILE` dumps every fact as JSON, read
  with whichever released schema the binding names; use it to compare ledgers.

Take a `db.backup` before and after a cutover. To redo a cutover, `db.restore`
the "before" backup into a fresh directory and run the step from that binding.

## Execute an authorized cutover

First create and independently restore a native backup with the current runtime.
Retain the original binding, all command/evidence files, and a complete fact and
report audit. Keep these in ignored private storage; public migrations contain
schema and transformation code only.

Retain a `TransitionContract` before dispatch: a UUIDv7 operation ID, the exact
source identity, the target identity with a fresh incarnation, and a hexadecimal
SHA-256 commitment to the chosen transformation and target snapshot. Reuse these
values for retries. Open the source using the generated source schema; queries
and their reader must use the same schema declaration. Release other direct
history handles for that directory before opening it.

Call `Transition.resolve` for a retained operation before proceeding. An already
activated result returns its original binding. A ready target is reused. For a
new or drained unpublished attempt, `Transition.begin` captures the source and
returns its frozen snapshot and population owner. Call the handwritten function
and then `population.finish()`. Batches can be incomplete; final admission checks
the whole target once. Scope cleanup releases owners without silently aborting.

Open the ready target in a nested scope and read it with `Transition.inspect`.
For the initial baseline, compare every fact, every relation count, and every
financial/report/work-register result against the captured source. Only the
native incarnation and state stamps change. Counts alone are insufficient.
For later reshapes, compare through the explicit application mapping.

Close the inspection scope before `Transition.activate`, then atomically adopt
the returned binding after checking that the configured binding still names the
expected source. Reopen through the ordinary CLI and audit again. Retain native
transition evidence and the original history/backup: prior-incarnation requests
remain evidence and are never replayed against the new authority.

After interruption, resolve the original contract. Never populate on top of a
ready target or infer failure from a missing caller response. An intentional
abandonment uses explicit `Transition.abort`, which fences the target before
thawing its matching source and refuses if activation already won.

The initial integration test verifies complete fact preservation, retained source
receipts, and retry after the target has accepted a subsequent command. Real
cutovers must also compare private facts and reports and verify a new backup.
